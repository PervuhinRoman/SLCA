# LABS_PLAN — StudentLedger

## Общий принцип

Каждая ЛР выполняется как часть одного проекта и разделяется на:

1. **Agent work**
2. **Human work**
3. **Evidence**
4. **Report**

ЛР переводится в `DONE` только после финального отчёта.

## Как продолжать работу и когда реализуется приложение

Текущий исполнитель продолжает одну согласованную задачу из `HANDOFF.md`.
Порядок получения изменений и передачи результата описан в README,
обязательные правила для агента — в AGENTS.md. Именных назначений нет.
Лабораторные используют результаты предыдущих: параллельные подзадачи
допустимы при согласованных границах, но не отменяют зависимости этапов.

Ниже — рабочее распределение уже заданных требований ТЗ по этапам,
а не дополнительные задания методички. Статус реализации и проверок
фиксируется в `REQUIREMENTS_MAP.md`, а не выводится из номера текущей ЛР.

| Этап | Реализация приложения, необходимая к этому моменту |
|---|---|
| ЛР2 | Только технический FastAPI-прототип `/health` |
| ЛР3 | Первый законченный сценарий записи и чтения данных через приложение для проверки persistence: PostgreSQL, SQLAlchemy, начальная схема Alembic, вход и необходимые ограничения ролей, добавление и просмотр студента (FR-02/FR-01); минимальная форма и список. Нужны безопасное создание начального администратора и аудит изменений; не создавать открытый CRUD без защиты |
| ЛР4–6 | Постепенно завершить FR-01–FR-14 и русский веб-интерфейс: сначала оставшуюся аутентификацию/управление пользователями, затем студентов, учебный план, оценки, ограничения преподавателя и аудит. Каждый шаг привязать к FR/SEC и проверкам в карте требований |
| ЛР7 | Проверить реализованные сценарии unit- и интеграционными тестами и в CI; минимум 40% функциональных требований — нижняя граница методички (при подсчёте по 14 FR — не менее 6), не замена финальной проверке всех FR по ТЗ |
| ЛР8 | Выполнить прослеживаемое изменение схемы и приложения в пределах ТЗ, ручной и автоматизированный этапы миграции, backup/восстановление; закончить проверку всех AC-01–AC-09 и оставшихся требований |

Alembic применяется с первого появления схемы, ЛР8 автоматизирует и
демонстрирует миграции. Backup перед изменением существующей схемы обязателен
по SEC-06, а не только после начала ЛР8. Не откладывать базовые ограничения
доступа до тестирования: предметные функции вводятся вместе с их защитой.
Неясности ТЗ уточнять перед соответствующей реализацией (например, допустимые
оценки и выбор элемента плана для FR-07), фиксируя решения в DECISIONS.

Если действие недоступно агенту, его результатом должна быть инструкция для
текущего исполнителя: где выполнить, команды/GUI-шаги, ожидаемый результат,
проверка и evidence. Сама инструкция не подтверждает выполнение действия.

# LR1 — Техническое задание

## Agent work
- сформировать ТЗ;
- обеспечить уникальные идентификаторы требований;
- согласовать роли, стек, критерии приёмки;
- поддерживать непротиворечивость документа.

## Human work
- проверить требования;
- согласовать замечания преподавателя;
- подписать/сдать финальную версию.

## Agent DoD
- требования непротиворечивы;
- ТЗ содержит роли, функции, NFR, критерии приёмки;
- актуальная версия определена как source of truth.

## Human DoD
- документ просмотрен;
- замечания преподавателя внесены;
- версия признана актуальной.

## Final task
Создать/обновить финальный отчёт ЛР1.

# LR2 — Виртуализация

## Цель
Подготовить TEST/STAGE/PROD на трёх Unix-подобных ВМ и запустить минимальный прототип проекта на TEST.

## Agent work
1. Прочитать актуальное ТЗ и методику ЛР2.
2. Проверить/создать минимальный FastAPI prototype (`GET /health`), если приложения ещё нет.
3. Определить одинаковую Unix-подобную ОС для трёх ВМ.
4. Предложить hostnames и схему IP.
5. Подготовить команды установки Git/Python/зависимостей.
6. Подготовить команды клонирования и запуска проекта на TEST.
7. Подготовить полный сценарий ping all-to-all.
8. Подготовить evidence checklist.
9. После получения фактических данных от человека обновить:
   - `PROJECT_CONTEXT.md`;
   - `LABS_STATUS.md`;
   - `HANDOFF.md`;
   - при необходимости `DECISIONS.md`.

## Agent DoD
- существует воспроизводимая инструкция настройки;
- минимальный проект запускается локально/может быть запущен на TEST;
- определены команды сетевой проверки;
- сформирован evidence checklist;
- агент не выдумывает результаты ручных действий.

## Human work
1. Установить гипервизор.
2. Создать 3 Unix VM:
   - TEST
   - STAGE
   - PROD
3. Настроить сеть.
4. Передать агенту реальные IP.
5. Проверить ping all-to-all.
6. На TEST:
   - установить Git;
   - клонировать проект;
   - установить зависимости;
   - запустить приложение.
7. Проверить `/health`.
8. Сделать скриншоты по evidence checklist.
9. Передать агенту реальные результаты.

## Human DoD
- 3 ВМ реально работают;
- все ВМ видят друг друга;
- репозиторий реально находится на TEST;
- приложение реально запущено на TEST;
- `/health` отвечает успешно;
- evidence собран.

## Evidence
Минимум:
- список/окно 3 ВМ;
- ОС и hostname каждой ВМ;
- IP каждой ВМ;
- ping TEST→STAGE/PROD;
- ping STAGE→TEST/PROD;
- ping PROD→TEST/STAGE;
- git clone;
- запуск приложения;
- успешный `/health`.

## Final task
После Agent DoD + Human DoD создать отчёт ЛР2 в DOCX, аналогичный по оформлению ЛР1, с реальными командами, результатами и скриншотами. После проверки отчёта установить `LR2 = DONE`.

# LR3 — Контейнеризация

## Agent work
- подготовить Dockerfile приложения;
- подготовить `docker-compose.yml` для приложения + PostgreSQL;
- добавить persistent volume;
- добавить `.env.example`;
- обеспечить отсутствие секретов в репозитории;
- подготовить команды сборки/запуска/логов;
- подготовить проверку persistence.

## Human work
- установить Docker/Docker Compose на TEST/STAGE/PROD;
- выполнить команды на реальных ВМ;
- записать данные через приложение;
- перезапустить контейнеры;
- подтвердить сохранность данных;
- собрать screenshots.

## Agent DoD
- `docker compose up -d --build` описан и воспроизводим;
- app и DB связаны;
- volume настроен;
- секреты вынесены;
- сценарий проверки DATA-04 готов.

## Human DoD
- Docker работает на всех 3 ВМ;
- контейнер приложения стартует;
- PostgreSQL стартует;
- данные сохраняются после restart;
- evidence собран.

## Final task
Создать отчёт ЛР3, аналогичный ЛР1.

- evidence собран.

## Human DoD

## Final task

## Agent work

- выбрать минимум 2 класса;
- рекомендуемый набор:
  - Ruff;
  - Bandit;
  - Gitleaks/TruffleHog;

- настроить fail conditions;
- подготовить безопасный демонстрационный дефект.

## Human work

- зафиксировать падение;
- исправить дефект;
- зафиксировать успешный pipeline;
- собрать evidence.

## Agent DoD

- критические проблемы валят build;
- есть сценарий negative/positive demonstration.

## Human DoD

- показан реальный successful build;
- evidence собран.

## Final task
Создать отчёт ЛР6, аналогичный ЛР1.

# LR7 — Автоматизированное тестирование

## Agent work
- выбрать pytest;
- разработать unit и integration tests;
- связать тесты с `FR-*`;
- покрыть >=40% функциональных требований;
- встроить tests в TeamCity до deploy;
- подготовить controlled bad-code scenario.

## Human work
- запустить failing test на плохом коде;
- затем successful runs для:
  - feature/fix;
  - dev;
  - prod;
- собрать evidence.

## Agent DoD
- unit + integration tests существуют;
- >=40% FR покрыто тестами;
- pipeline запускает тесты на всех ветках;
- deploy не идёт при failed tests.

## Human DoD
- зафиксирован один реальный failed run;
- зафиксированы successful runs feature/dev/prod;
- evidence собран.

## Final task
Создать отчёт ЛР7, аналогичный ЛР1.

## Agent work
- создать `db/schema/`;

- добавить проверку SQL в pipeline;
- подготовить реальное изменение схемы;

- подтвердить работу приложения;
- затем проверить автоматизированную миграцию;
- выполнить запуск PROD pipeline;
- подтвердить создание backup;
- собрать evidence.

## Agent DoD
- схема хранится как code/artifact;
- SQL security check встроен;
- Alembic migrations воспроизводимы;
- STAGE auto-migration реализована;
- PROD pipeline содержит backup → migrate → deploy → smoke test.

## Human DoD
- ручной этап STAGE реально показан;
- auto migration реально показана;
- схемы сравниваются;
- PROD backup реально создан;
- evidence собран.

## Final task
Создать отчёт ЛР8, аналогичный ЛР1.

# Общий Definition of Done проекта

Проект завершён, когда:
- LR1—LR8 имеют статус `DONE`;
- все отчёты созданы;
- source of truth актуален;
- context-файлы соответствуют фактической реализации;
- pipeline TEST/STAGE/PROD воспроизводим;
- секреты не находятся в Git;
- миграции и backup проверены;
- финальный `HANDOFF.md` описывает состояние завершённого проекта.
