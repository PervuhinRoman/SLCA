# LABS_PLAN — StudentLedger

## Общий принцип

Каждая ЛР выполняется как часть одного проекта и разделяется на:

1. **Agent work**
2. **Human work**
3. **Evidence**
4. **Report**

ЛР переводится в `DONE` только после финального отчёта.

## Как продолжать работу и когда реализуется приложение

Текущий исполнитель продолжает одну согласованную задачу из `HANDOFF.md`.
Порядок получения изменений и передачи результата описан в README,
обязательные правила для агента — в AGENTS.md. Именных назначений нет.
Лабораторные используют результаты предыдущих: параллельные подзадачи
допустимы при согласованных границах, но не отменяют зависимости этапов.

Ниже — рабочее распределение уже заданных требований ТЗ по этапам,
а не дополнительные задания методички. Статус реализации и проверок
фиксируется в `REQUIREMENTS_MAP.md`, а не выводится из номера текущей ЛР.

| Этап | Реализация приложения, необходимая к этому моменту |
|---|---|
| ЛР2 | Только технический FastAPI-прототип `/health` |
| ЛР3 | Первый законченный сценарий записи и чтения данных через приложение для проверки persistence: PostgreSQL, SQLAlchemy, начальная схема Alembic, вход и необходимые ограничения ролей, добавление и просмотр студента (FR-02/FR-01); минимальная форма и список. Нужны безопасное создание начального администратора и аудит изменений; не создавать открытый CRUD без защиты |
| ЛР4–6 | Включить CI/CD и статический анализ; провести редактирование студента через feature → PR/review → STAGE. Основную функциональность добавлять после появления CI по плану PR ниже |
| ЛР7 | Завершить управление пользователями и проверить минимум 6 из 14 FR (FR-01/02/03/11/12/14) unit- и интеграционными тестами в CI. Это не замена финальной проверке всех FR |
| После ЛР7 и ЛР8 | Добавить подсчёт студентов и учебные планы; журнал оценок и назначения преподавателей использовать для реальных ручной и автоматизированной миграций, затем PROD и полная приёмка |

Alembic применяется с первого появления схемы, ЛР8 автоматизирует и
демонстрирует миграции. Backup перед изменением существующей схемы обязателен
по SEC-06, а не только после начала ЛР8. Не откладывать базовые ограничения
доступа до тестирования: предметные функции вводятся вместе с их защитой.
Неясности ТЗ уточнять перед соответствующей реализацией (например, допустимые
оценки и выбор элемента плана для FR-07), фиксируя решения в DECISIONS.

Если действие недоступно агенту, его результатом должна быть инструкция для
текущего исполнителя: где выполнить, команды/GUI-шаги, ожидаемый результат,
проверка и evidence. Сама инструкция не подтверждает выполнение действия.

## План разработки через PR

Уточнён 2026-10-10: пользователь запросил PR **только реализации
веб-приложения**, а не всех работ проекта. Этот раздел заменяет прежний
смешанный список PR-00–18. APP-01–10 — обозначения будущих PR приложения,
не номера GitHub. Docker, TeamCity, правила веток, pipeline и отчёты остаются
в разделах лабораторных ниже и не входят в этот список.

### Общие условия

- До начала параллельной работы согласовать её границы и отдельную ветку:
  ADR-009 уже определяет временные ветки от dev, PR в dev и выпуск dev → prod.
  Ветки dev/prod опубликованы; защита GitHub ещё не настроена, CI отсутствует.
  APP-01–03 сейчас не выполняются; текущая задача — документация ЛР1/веток.
- APP-01–03 можно готовить локально после согласования, пока товарищ делает
  ЛР2. Сохранить фиксированный SHA прототипа для его демонстрации. Переход
  к стендовым работам следующей ЛР требует завершения предыдущей и её отчёта.
- После APP-03 остановить расширение продукта до появления рабочего CI/CD.
  APP-04 создаётся как реальное изменение после настройки доставки для ЛР5.
- С каждой функцией идут русский UI, серверная авторизация, валидация,
  аудит изменений и значимые unit/integration-тесты. Swagger не заменяет UI.
  Тесты запускаются локально с начала разработки и в CI сразу после его
  настройки; ждать ЛР7 для написания тестов не нужно.
- Схема меняется через Alembic с первого PR. Перед изменением существующей
  БД — backup и проверенная процедура восстановления. До автоматизации
  миграции STAGE выполняются вручную по инструкции перед deploy.
- CI, публикация образов, deploy, SQL-анализ и защита merge — внешние
  зависимости этих PR. Их настройка и проверка остаются работами соответствующих
  ЛР. Красный статус CI сам по себе не означает запрета merge на GitHub.
- Нереализованные функции не выдаются за выполненные требования. Временное
  отсутствие журнала у преподавателя до APP-09 — ограничение неполной версии,
  а не изменение ролевой модели ТЗ. Нельзя предоставлять доступ без защиты.

### APP-01 — Основа приложения и хранение данных

**Когда:** сейчас, после согласования параллельной работы. **Зависимости:** нет.
**Состав:** конфигурация окружения, PostgreSQL/SQLAlchemy, начальная миграция
Alembic; User, Student, AuditLog и хранение отзыва refresh-токенов. PK/FK,
User–Student 1:1, закреплённые зависимости, `.env.example`, безопасная обработка
ошибок и журналирование. Контракт `/health` сохраняется.
**Готовность:** схема создаётся на чистой БД; ошибочная транзакция не оставляет
частичных данных; секреты не записываются в Git/логи; инструкция подключения,
backup/restore проверена. Это фундамент, пользовательских функций ещё нет.
**Требования:** основа SYS-03, REL-01–04, DATA-01/03, INF-01/02,
SW-01/02/04/06/08, SEC-03–06.

### APP-02 — Вход, выход и пользовательская сессия

**Когда:** после APP-01, можно параллельно ЛР2.
**Состав:** русская страница входа, JWT access/refresh, refresh/logout,
истечение сессии, хеш пароля; безопасная команда создания первого
администратора. Проверка текущей роли/активности на сервере, отзыв refresh.
**Готовность:** правильный вход успешен; неправильный пароль не раскрывает
причину; истечение access и отзыв refresh работают; 401 без аутентификации,
403 без права. Публичной незащищённой регистрации нет.
**Требования:** FR-11/12, основа FR-13, SEC-01/07/08/09, UI-01–04.

### APP-03 — Добавление и просмотр студентов

**Когда:** после APP-02; завершить к контейнеризации в ЛР3.
**Состав:** форма добавления студента администратором; список для
администратора/преподавателя; собственная запись студента. ФИО, год
поступления, форма обучения, группа, связь с User; валидация и аудит.
До APP-05 тестовые роли создаются контролируемыми фикстурами.
**Готовность:** запись сохраняется и доступна после перезапуска; студент
не читает чужие сведения даже по прямому URL. Этот сценарий используют
для проверки сохранности данных в ЛР3. Редактирование пока не добавлять.
**Требования:** FR-01/02, частично FR-13, SEC-04/09/10, SYS-02, UI-01–04.
**Рубеж:** минимальное приложение готово для ЛР3–4; далее дождаться CI/CD.

### APP-04 — Редактирование студента

**Когда:** после APP-03, завершённой ЛР4 и настройки доставки на STAGE
в ЛР5. CI должен реально собирать feature-ветку и запускать имеющиеся тесты.
**Состав:** форма и API изменения сведений администратором; валидация,
аудит и тесты. Схема не меняется.
**Готовность:** feature-build → PR → review другого участника → merge →
автоматическое обновление STAGE. Изменённые значения видны после повторного
запроса; прямой API не обходит права. Это функциональная демонстрация ЛР5.
**Требования:** FR-03, SEC-09/10.

### APP-05 — Пользователи и административный интерфейс

**Когда:** после APP-04 и ЛР6: CI/CD и статический анализ работают;
выполнить до демонстрации тестового покрытия ЛР7.
**Состав:** создание пользователей, назначение и изменение ролей,
блокировка, инициирование сброса пароля; Teacher с User 1:1, привязка
профилей студентов; просмотр аудита администратором. Механизм сброса
конкретизировать до реализации в рамках ТЗ, без обязательного почтового сервиса.
**Готовность:** созданный пользователь входит; новая роль действует со
следующего запроса; блокировка прекращает доступ и отзывает refresh;
другие роли не управляют пользователями и не читают аудит.
**Требования:** FR-14, SEC-07/09/10, ТЗ §3.2, INF-01.
**Рубеж ЛР7:** после этого доступны шесть полных требований для unit/integration
проверок: FR-01/02/03/11/12/14 — 6/14 = 42,9% функциональных требований,
не строк кода. ЛР7 отдельно требует плохой код → failed run и успешные прогоны
FEATURE/FIX, DEV, PROD; общий FR-13 ещё не считать полностью закрытым.

### APP-06 — Подсчёт студентов по форме обучения

**Когда:** после APP-05 и ЛР7; все настроенные проверки уже обязательны
в командном процессе.
**Состав:** выбор формы обучения и отображение количества студентов;
доступ в пределах ролевых прав ТЗ, без раскрытия студенту агрегатов чужих данных.
**Готовность:** результат совпадает с контрольным SQL; проверены пустой
набор и разные формы обучения, интерфейс работает на STAGE.
**Требования:** FR-04, SEC-09.

### APP-07 — Дисциплины и учебные планы

**Когда:** после APP-06; до журнала оценок.
**Состав:** Discipline, CurriculumItem и миграции; справочник дисциплин,
просмотр учебного плана, добавление/изменение администратором; часы и форма
отчётности выбранной дисциплины. Студенты/преподаватели только читают.
До реализации согласовать выбор элемента плана для FR-07, если дисциплина
входит в несколько планов.
**Готовность:** API и UI соответствуют FR-05/06/07, неверные данные
отклоняются, изменения аудируются. Существующую STAGE-БД обновить вручную
после backup до deploy: автоматизация миграций ещё впереди.
**Требования:** FR-05–07, DATA-01/03, INF-01/02, SEC-06/09/10.

### APP-08 — Первая версия журнала оценок

**Когда:** после APP-07; в ЛР8 уже подготовлены хранение схемы и SQL-анализ,
но автоматическая миграция STAGE ещё не включена. Согласованы допустимые
оценки и учебные периоды.
**Состав:** Grade с FK к Student/Discipline, просмотр и добавление оценок
администратором, просмотр собственных оценок студентом; UI, аудит, тесты,
новая миграция и актуальная выгрузка схемы. До APP-09 журнал преподавателя
закрыт: ещё нет назначений дисциплин; FR-08/09 реализованы частично.
**Готовность:** протестировать на TEST → backup STAGE → вручную применить
миграцию STAGE → merge/deploy → проверить UI и сохранность данных.
Несуществующие Student/Discipline отклоняются самой БД.
**Требования:** часть FR-08/09, DATA-02; демонстрация ЛР8, пп. 4–8.

### APP-09 — Журнал преподавателя и изменение оценок

**Когда:** после APP-08, подтверждения ручной миграции и настройки
автоматических миграций STAGE в ЛР8.
**Состав:** TeachingAssignment, управление назначениями администратором;
преподаватель просматривает/добавляет/изменяет оценки только по своим
дисциплинам, администратор изменяет любые оценки; студент только читает свои.
UI, серверные проверки, аудит, миграция и dump. Новая таблица даёт второе
реальное изменение схемы в рамках ТЗ.
**Готовность:** CI/review → merge → backup → автоматическая миграция →
deploy → сравнение схем и smoke. Смена назначения сразу влияет на доступ;
подмена ID не обходит ограничения; данные сохранены.
**Требования:** завершение FR-08/09/10/13, INF-01/02, SEC-09/10;
демонстрация автоматической миграции ЛР8, п. 11.

### APP-10 — Доведение приложения до полной приёмки

**Когда:** после APP-09; до окончательного выпуска на PROD. Повторить
затронутые проверки после фактического развёртывания на PROD.
**Состав:** исправления найденных дефектов, единообразные русские сообщения
и подписи полей, обработка недоступности БД; полные тесты FR/SEC/REL/DATA/UI,
синтетические данные и нагрузочный сценарий. Новые функции сверх ТЗ не добавлять.
README и описание модели/настроек актуализируются вместе с приложением.
**Готовность:** все FR-01–14 и применимые критерии AC подтверждены;
≥1000 студентов, ≥100 дисциплин, ≥10000 оценок; не менее 95% запросов
просмотра/сохранения ≤3 с при 10 одновременных пользователях. Нет частичных
записей при ошибке, утечек секретов или критических дефектов; роли проверены
в UI и API, чистый запуск/restart/persistence воспроизводимы.
EVOL-01 оценивается по структуре решения, без реализации импорта и новых ролей.
**Граница:** настройка PROD pipeline/backup и отчёты ЛР — отдельные работы.
Финальная приёмка проекта требует и их реальных подтверждений; завершение
APP-10 само по себе не закрывает ЛР8 или весь проект.

### Готовность, передача и evidence

Для каждого PR агент готовит код, миграции при необходимости, тесты,
инструкции и обновляет HANDOFF/карту требований. Человек выполняет
недоступные агенту действия, review и ручные UI-проверки; доступные агенту
действия могут быть поручены ему. До CI проверки локальные, после его
появления прикладываются реальные build ID и результаты pipeline.
Evidence: SHA и URL PR, результаты тестов, скриншоты изменённого UI по ролям;
для APP-08/09 — дополнительно backup, ревизии схем, ручная/автоматическая
миграция и работа обновления на STAGE. Секреты и содержимое backup в Git
не помещать. Команды уточняются при реализации по фактической среде.
Тесты каждой новой функции входят в её PR, а не откладываются до APP-10.

Источники: актуальное ТЗ §3.2, §4–7; методичка ЛР3 (стр. 11, 15),
ЛР5 (стр. 21–22), ЛР7 (стр. 30), ЛР8 (стр. 34–35).
Распределение функций по времени — рабочая рекомендация команды,
а не запрет методички реализовать их раньше. Номера PR не подтверждают
выполнение лабораторных. Отчёт создаётся после реальных результатов всей ЛР,
отдельного отчёта на PR приложения не требуется.

# LR2 — Виртуализация

## Цель
Подготовить TEST/STAGE/PROD на трёх Unix-подобных ВМ и запустить минимальный прототип проекта на TEST.

## Agent work
1. Прочитать актуальное ТЗ и методику ЛР2.
2. Проверить/создать минимальный FastAPI prototype (`GET /health`), если приложения ещё нет.
3. Определить одинаковую Unix-подобную ОС для трёх ВМ.
4. Предложить hostnames и схему IP.
5. Подготовить команды установки Git/Python/зависимостей.
6. Подготовить команды клонирования и запуска проекта на TEST.
7. Подготовить полный сценарий ping all-to-all.
8. Подготовить evidence checklist.
9. После получения фактических данных от человека обновить:
   - `PROJECT_CONTEXT.md`;
   - `LABS_STATUS.md`;
   - `HANDOFF.md`;
   - при необходимости `DECISIONS.md`.

## Agent DoD
- существует воспроизводимая инструкция настройки;
- минимальный проект запускается локально/может быть запущен на TEST;
- определены команды сетевой проверки;
- сформирован evidence checklist;
- агент не выдумывает результаты ручных действий.

## Human work
1. Установить гипервизор.
2. Создать 3 Unix VM:
   - TEST
   - STAGE
   - PROD
3. Настроить сеть.
4. Передать агенту реальные IP.
5. Проверить ping all-to-all.
6. На TEST:
   - установить Git;
   - клонировать проект;
   - установить зависимости;
   - запустить приложение.
7. Проверить `/health`.
8. Сделать скриншоты по evidence checklist.
9. Передать агенту реальные результаты.

## Human DoD
- 3 ВМ реально работают;
- все ВМ видят друг друга;
- репозиторий реально находится на TEST;
- приложение реально запущено на TEST;
- `/health` отвечает успешно;
- evidence собран.

## Evidence
Минимум:
- список/окно 3 ВМ;
- ОС и hostname каждой ВМ;
- IP каждой ВМ;
- ping TEST→STAGE/PROD;
- ping STAGE→TEST/PROD;
- ping PROD→TEST/STAGE;
- git clone;
- запуск приложения;
- успешный `/health`.

## Final task
После Agent DoD + Human DoD создать отчёт ЛР2 в DOCX, аналогичный по оформлению ЛР1, с реальными командами, результатами и скриншотами. После проверки отчёта установить `LR2 = DONE`.
