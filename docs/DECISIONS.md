# DECISIONS — StudentLedger

Здесь фиксируются решения, которые нельзя заставлять следующего агента угадывать.

## ADR-001 — Backend: FastAPI
**Status:** accepted
**Decision:** серверная часть реализуется на FastAPI.
**Source:** актуальное ТЗ ЛР1.

## ADR-002 — Database: PostgreSQL 16+
**Status:** accepted
**Decision:** используется PostgreSQL версии 16 или выше; минимальная версия — 16.
**Reason:** версия находится в официальном цикле поддержки и получает исправления ошибок и безопасности.
**Source:** актуальное ТЗ ЛР1.

**Status:** accepted
**Decision:** SQLAlchemy используется как ORM, Alembic — для миграций схемы.
**Source:** актуальное ТЗ ЛР1.

## ADR-009 — Ветки по методичке и изменение SW-09
**Status:** accepted by user; dev/prod защищены, CI ожидается
**Date:** 2026-10-10
**Основание:** пользователь явно выбрал приоритет методички и поручил
изменить SW-09. Ранее SW-09 задавал main → PROD, release/* → STAGE,
develop → TEST; это расходилось с ЛР5, пп. 5–6 (стр. 22), и ЛР8,
пп. 7/10–12 (стр. 34–35): DEV → STAGE, отдельный выпуск на PROD.
**Decision:** постоянные dev и prod; временные feature/fix/docs/chore
создаются от dev и сливаются PR в dev. CI выполняется на TEST; успешная
интеграция dev доставляется на STAGE. Проверенная на STAGE версия через
PR dev → prod выпускается на PROD. Изменение ТЗ внесено в исходный DOCX
и PDF-представление. Согласование преподавателем не заявляется.
**Процесс:** для кода, конфигурации, инструкций, ТЗ и отчётов — единые
ветки/PR, проверки и review другого участника. Документация к функции
передаётся с кодом; отдельная правка инструкций — docs/*.
Тесты/сборка по требованиям методички не пропускаются из-за docs-only.
Подробные правила и порядок перехода — README, раздел «Совместная работа».
**Последствия:** прежняя SW-09 заменена осознанно, прежняя схема не считается
выполненной. main/develop/release/* больше не являются целевыми ветками.
master — историческая база, не ветка окружения. ADR-012 заменён этим решением.
Ветки dev/prod созданы и опубликованы 2026-10-10 от master 816ac3e;
документационные изменения идут через docs/lr1-branch-workflow.
Default branch — dev; dev/prod защищены, master заблокирована. После
обновления прав токена настройки применены и проверены через API.
CI отсутствует; APP-01–03 не выполняются. Временное исключение — ADR-014.

## ADR-010 — Граница прототипа ЛР2
**Status:** accepted
**Date:** 2026-10-09
**Decision:** по LABS_PLAN реализуется только FastAPI `GET /health`,
возвращающий HTTP 200 и `{"status":"ok"}`. Роут проверяет жизнь процесса;
продуктовых данных не раскрывает, защищённых функций пока нет.

БД, JWT, роли и бизнес-функции остаются требованиями последующих этапов.
**Trace:** SYS-01, SW-01 частично; G-05 и AC-02 не закрыты.

## ADR-014 — Самостоятельное слияние до ЛР5
**Status:** accepted by user after explicit warning, 2026-10-10.
Пользователь подтвердил временное отступление от SW-09 и требования ЛР5,
п. 5, стр. 22 методички: «с требованием согласования со стороны другого
члена команды». До ЛР5 автор может сам слить PR без чужого одобрения.
Это не выполнение исходного требования о согласовании; DOCX/PDF SW-09
сохраняют целевое требование, исключение явно документировано здесь.

Фактически настроено: default dev; dev/prod требуют PR и закрытых обсуждений,
required_approving_review_count=0, enforce_admins=true, без force push и
удаления. dismiss_stale_reviews=true сохранён, но чужое approval сейчас
не является условием merge. require_last_push_approval=false, code owners
и linear history не требуются. CI отсутствует, required_status_checks=null.
Master — Lock branch с запретом удаления/force push, правила действуют и
для администраторов. Обход PR/будущего CI не разрешён.

Перед выполнением ЛР5 включить минимум одно одобрение для dev/prod и получить
реальное review другого участника на демонстрационном PR. После появления
TeamCity отдельно настроить фактический required check и актуальность ветки.
Источник результата: docs/evidence/branch-workflow-check.md.

**Decision:** текущая совместная работа и первая публикация ведутся в `master`;
дополнительные ветки сейчас не создаются. Remote, указанный пользователем:
`https://github.com/PervuhinRoman/SLCA.git`.
**Scope:** организация текущей работы. Назначение веток окружениям из SW-09
ещё не пересмотрено; `master` не назначается автоматически PROD.
ADR-009 остаётся открытым до ЛР4; требуемые методичкой ветки и PR будут
согласованы перед соответствующим этапом. Исходное ТЗ не редактировалось.

## ADR-015 — Соблюдение схемы веток dev/prod для работ по ЛР2
**Status:** accepted
**Date:** 2026-10-10
**Decision:** работы по ЛР2 (стенды, скрипты, evidence, обновление контекста)
выполнялись локально на базе прежней ветки `master` до публикации ADR-009,

**Note:** конфликт `docs/DECISIONS.md` при объединении разрешён по фактическому
состоянию обеих работ: решения ADR-013/ADR-014 другого участника сохранены,

## ADR-017 — Ресурсы виртуальных машин ЛР2
**Status:** accepted
**Date:** 2026-10-09
**Decision:** на каждую ВМ — 2 vCPU, 3 ГБ RAM, 25 ГБ диска, 64 МБ видеопамяти
(контроллер VMSVGA, включённый буфер обмена). RAM поднята с исходных
предложенных 2 ГБ, потому что по требованию текущего исполнителя на ВМ
устанавливается графический интерфейс; 2 ГБ для рабочего стола мало,
а 3 ГБ дают три стенда суммарно 9 ГБ, что укладывается в память хоста.
**Reason:** баланс «минимальный GUI без потери производительности».
**Note:** 25 ГБ на диске выбраны с запасом под ЛР3 (Docker, PostgreSQL),
а не только под ЛР2.

## ADR-019 — Минимальный графический интерфейс на ВМ
**Status:** accepted
**Date:** 2026-10-09
**Decision:** по требованию текущего исполнителя на трёх ВМ устанавливается
минимальный графический интерфейс, оптимизированный по ресурсам:
пакетный набор `xubuntu-desktop-minimal` (среда XFCE, дисплейный менеджер
LightDM) вместо полного `ubuntu-desktop`, плюс текстовые утилиты,
необходимые лабораторным. Графическая оболочка не заменяет CLI: все
лабораторные операции выполняются командами, браузер используется только
для демонстрации веб-интерфейса приложения.
**Reason:** XFCE — минимальный из поддерживаемых в Ubuntu рабочих столов,
работает на 3 ГБ RAM без заметных задержек.
**Note:** предметный веб-интерфейс StudentLedger (UI-01–UI-04) к этому
решению отношения не имеет и реализуется в приложении, а не в ОС ВМ.

## ADR-020 — Сеть стендов ЛР2
**Status:** accepted
**Date:** 2026-10-09
**Decision:** у каждой ВМ два адаптера: `nic1` — NAT (загрузка пакетов,
Git, SSH с хоста), `nic2` — общий сегмент VirtualBox Host-Only
`VirtualBox Host-Only Ethernet Adapter` (192.168.56.0/24). Адреса
внутреннего сегмента: TEST 192.168.56.11, STAGE 192.168.56.12,
PROD 192.168.56.13, маска /24. DHCP на host-only отключён, адреса
назначаются статически; сопоставление адаптера задаётся по MAC-адресу.
**Reason:** связь «все со всеми» между тремя ВМ и с хостом, как требует
ЛР2, без изменения физической локальной сети.
**Note:** предложение из `LR2_RUNBOOK.md` о внутренней сети `intnet`
уточнено на host-only, чтобы хост тоже мог проверять `/health`.

## ADR-021 — Учётные данные лабораторных стендов
**Status:** accepted for lab use
**Date:** 2026-10-09
**Decision:** на всех трёх ВМ создаётся пользователь `student` с паролем
лабораторного стенда. Пароль передаётся установщику и используется только
внутри изолированных ВМ учебного проекта.
**Security note:** это лабораторный пароль, а не секрет продукта. Для ЛР3–ЛР8
он подлежит замене: SEC-03 требует отсутствия секретов в репозитории,
поэтому реальные пароли БД и CI в документацию и Git не попадают.

## ADR-022 — Ограничение по памяти хоста при работе трёх стендов
**Status:** accepted, требуется соблюдение
**Date:** 2026-10-09
**Decision:** одновременно запускать три стенда можно только при свободной
памяти хоста не менее ~10 ГБ. Каждая ВМ занимает 3 ГБ; при нехватке памяти
VirtualBox переводит гостя в состояние `GURU_MEDITATION` и установка/работа
срывается.
**Факт сбоя:** первая автоматическая установка TEST 2026-10-09 23:05
завершилась аварийно через ~1 минуту. В логе ВМ:
`Host RAM: 16167MB (15.7GB) total, 539MB available`, далее
`pgmPhysGCPhys2CCPtrInternal failed ... VERR_MAP_FAILED`,
`Failed to procure handy pages; rc=VERR_NO_PAGE_MEMORY`,
`Changing the VM state from 'RUNNING' to 'GURU_MEDITATION'`.
Снимок экрана: `docs/evidence/lr02/vbox-test-installer-crash.png`.
**Меры:** перед запуском трёх ВМ закрывать тяжёлые приложения и не держать
включённой постороннюю ВМ `kali` (она заявляет 11 ГБ RAM); установку стендов
выполнять поочерёдно; контролировать свободную память.
**Reason:** это ограничение учебного хоста (15,7 ГБ RAM), а не дефект
конфигурации стендов. В отчёте ЛР2 указывается как фактическое условие
воспроизводимости.
