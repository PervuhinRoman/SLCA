# ЛР2 — Виртуализация: инструкция выполнения

Сверка с ТЗ выполнена: `SOURCE_REVIEW.md`. Эта инструкция — план действий,
а не подтверждение существования стендов. Фактические значения и результаты
заполняются в `evidence/lr02/README.md` после выполнения.

## 1. Виртуальные машины

Для всех трёх ВМ выбрана **Ubuntu Server 24.04 LTS, Python 3.12**.
Используйте один и тот же установочный образ для всех стендов.
Официальные образы: [AMD64](https://releases.ubuntu.com/24.04/),
[ARM64](https://cdimage.ubuntu.com/releases/24.04/release/).
Архитектура должна соответствовать возможностям хоста и гипервизора.
Конкретный гипервизор уточняется у человека; методичка разрешает выбор студента.

Предлагаемые стартовые ресурсы на каждую ВМ: 2 vCPU, 2 ГиБ RAM,
20 ГиБ диска. Это оценка для ЛР2, не ресурсный расчёт будущего TeamCity.
На хосте должно хватать ресурсов для одновременной работы трёх ВМ.

| Стенд | Предлагаемый hostname | Пример адреса внутренней сети |
|---|---|---|
| TEST | studentledger-test | 192.168.56.11/24 |
| STAGE | studentledger-stage | 192.168.56.12/24 |
| PROD | studentledger-prod | 192.168.56.13/24 |

**Адреса — только предложение, не реальные IP.** Перед применением проверить,
что подсеть не пересекается с сетью хоста/VPN и адреса не заняты.

1. Установить выбранный гипервизор, записать название и версию.
2. Создать три отдельные ВМ, подключить один образ Ubuntu, установить ОС.
3. Каждой ВМ выделить отдельный диск и уникальный MAC-адрес.
4. На каждой задать hostname (пример для TEST):

```bash
sudo hostnamectl set-hostname studentledger-test
```

На STAGE/PROD использовать соответствующие имена из таблицы.

## 2. Сеть

Схема: у каждой ВМ первый адаптер NAT для загрузки пакетов и доступа к Git;
второй — одна общая внутренняя/host-only сеть для TEST/STAGE/PROD.
Все три вторых адаптера подключаются к одному виртуальному сегменту.
Обычный отдельный NAT каждой ВМ сам по себе не гарантирует связь между ВМ.

Если гипервизор предлагает общую NAT network с обменом между гостями,
допустима одна такая сеть; фактическую схему записать в evidence.
Для двух адаптеров маршрут по умолчанию и DNS оставлять на NAT-адаптере.

На каждой ВМ через её консоль:

```bash
ip -br link
ip -br -4 address
ip route
ls /etc/netplan
```

Для внутреннего адаптера настроить уникальный статический адрес через
Netplan. Сначала посмотреть существующий YAML: не дублировать описание уже
настроенного интерфейса. Пример фрагмента для TEST (имя `enp0s8` заменить
реальным, адрес — согласованным):

```yaml
network:
  version: 2
  ethernets:
    enp0s8:
      dhcp4: false
      addresses:
        - 192.168.56.11/24
```

Сохранить фрагмент в `/etc/netplan/60-studentledger.yaml`, если внутренний
интерфейс ещё не описан в другом файле; иначе изменить его существующее описание.
NAT-интерфейс и его DHCP не удалять. На STAGE/PROD заменить адрес.

```bash
sudo chmod 600 /etc/netplan/60-studentledger.yaml
sudo netplan generate
sudo netplan try
ip -br -4 address
ip route
```

Если редактировался другой файл, в `chmod` использовать именно его путь.
В `netplan try` подтвердить настройки только при сохранении связности.
Работать из консоли гипервизора, чтобы иметь доступ при ошибке сети.

## 4. Проверка «от всех ко всем»

На **каждой** ВМ в Bash задать фактические адреса:

```bash
read -r -p 'Фактический IP TEST: ' TEST_IP
read -r -p 'Фактический IP STAGE: ' STAGE_IP
read -r -p 'Фактический IP PROD: ' PROD_IP
hostname
ip -br -4 address
```

На TEST:

```bash
ping -c 4 -W 2 "$STAGE_IP"
ping -c 4 -W 2 "$PROD_IP"
```

На STAGE:

```bash
ping -c 4 -W 2 "$TEST_IP"
ping -c 4 -W 2 "$PROD_IP"
```

На PROD:

```bash
ping -c 4 -W 2 "$TEST_IP"
ping -c 4 -W 2 "$STAGE_IP"
```

Критерий: все шесть направлений успешны, в каждом 4 ответа и 0% потерь.
При ошибке проверить состояние адаптеров, общий сегмент, маски, уникальность
IP/MAC, `ip route` и правила ICMP в firewall. Не отключать firewall целиком.

## 5. Первоначальная публикация (исторический шаг ЛР2)

На момент начала ЛР2 `.git` и remote отсутствовали. Человек создаёт пустой
удалённый репозиторий в выбранном Git-сервисе и задаёт доступ участникам.
URL не должен содержать пароль или токен. Аутентификация — через SSH-ключ
или менеджер учётных данных Git-сервиса.

В локальном каталоге StudentLedger после проверки изменений:

```bash
git init -b master
git add .gitignore AGENTS.md HANDOFF.md README.md requirements.txt app docs
git diff --cached --stat
git diff --cached
git commit -m "Prepare LR2 FastAPI prototype and VM runbook"
```

Эта публикация в `master` уже выполнена 2026-10-09; команды выше/ниже
сохранены для описания начального шага и не повторяются в существующем repo.
С 2026-10-10 принята dev/prod-схема ADR-009; порядок перехода — README.
При отсутствии имени/email Git установить собственные
значения локально: `git config user.name` и `git config user.email` с аргументами.
В Bash задать URL созданного remote и отправить коммит:

```bash
REPO_URL=https://github.com/PervuhinRoman/SLCA.git
git remote add origin "$REPO_URL"
git push -u origin master
```

Если репозиторий уже существует, сначала проверить `git status` и
`git remote -v`; не повторять инициализацию, добавление remote или менять ветку
вслепую. Проверить доступность отправленного коммита перед клонированием.

## 6. Клонирование и запуск на TEST

Для ЛР2 используется исторический прототип в master. Перед запуском
сверить SHA с согласованной версией прототипа; не обновлять стенд товарища
на новую версию без согласования. После фактического перехода новая
разработка идёт от dev; это не меняет сохранённые evidence ЛР2.

В Bash на TEST:

```bash
REPO_URL=https://github.com/PervuhinRoman/SLCA.git
git clone --branch master "$REPO_URL" StudentLedger
cd StudentLedger
git branch --show-current
git rev-parse HEAD
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
read -r -p 'Фактический IP внутреннего адаптера TEST: ' TEST_IP
.venv/bin/python -m uvicorn app.main:app --host "$TEST_IP" --port 8000
```

Сервер оставить работающим. В другом терминале TEST или на STAGE/PROD:

```bash
read -r -p 'Фактический IP TEST: ' TEST_IP
curl --fail-with-body --max-time 5 -i "http://${TEST_IP}:8000/health"
```

Ожидается HTTP 200 и `{"status":"ok"}`. Это ожидаемый результат,
фактический ответ необходимо сохранить. Приложение слушает только внутренний
IP TEST. Если UFW активен, разрешить TCP/8000 только из выбранной внутренней
подсети; пример при использовании предложенной адресации:
`sudo ufw allow from 192.168.56.0/24 to any port 8000 proto tcp`.
Не настраивать проброс порта из Интернета. Остановка — Ctrl+C.

## 7. Подтверждения и завершение

Заполнить [evidence checklist](evidence/lr02/README.md), передать реальные IP,
команды, результаты и скриншоты. После этого обновляются контекст и handoff,
создаётся и проверяется отчёт DOCX по стилю ЛР1. Только затем LR2 = DONE.

Agent DoD: прототип запускается, зависимости закреплены, команды настройки,
шесть ping и evidence checklist подготовлены. Human DoD: три ВМ работают,
инструменты установлены на всех, сеть проверена, remote клонирован и прототип
работает на TEST, подтверждения собраны.

## 8. Подготовка к защите

1. Virtual network объединяет виртуальные адаптеры. Внутренняя сеть связывает
   гостей; host-only обычно также даёт доступ хосту. Bridge подключает ВМ к
   физической LAN как отдельный узел. NAT преобразует исходящие адреса гостей;
   входящие соединения обычно требуют отдельной настройки. Изоляция и связь
   гостей зависят от режима конкретного гипервизора.
2. В полной ВМ Linux-системные вызовы обрабатывает гостевое ядро Linux.
   Гипервизор предоставляет виртуальное оборудование и управляет выполнением
   гостя; Windows не переводит каждый Linux syscall в Win32 API.
3. Виртуальный диск обычно хранится файлом/набором файлов на файловой системе
   хоста. Гостю он представлен блочным устройством со своей таблицей разделов
   и файловой системой; читать ext4 на уровне файлов хосту для этого не нужно.

[Ubuntu Netplan](https://documentation.ubuntu.com/server/explanation/networking/configuring-networks/).
