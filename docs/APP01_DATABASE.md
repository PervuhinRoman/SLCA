# APP-01: конфигурация и хранение данных

Основа приложения, без пользовательских функций. HTTP-контракт `/health`
сохранён: `200 {"status":"ok"}` даже при недоступной БД. Проверка БД —
отдельная локальная команда; публичных CRUD и диагностических маршрутов нет.
JWT, хеширование паролей и RBAC реализуются в APP-02, студенты — в APP-03.

## Конфигурация и запуск

Нужны Python 3.12 и PostgreSQL 16+ в локальной/изолированной сети.
Для PostgreSQL выбирайте актуальную минорную версию своей ветки.
Из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
cp .env.example .env
chmod 600 .env
```

В редакторе заполните `.env`: снимите комментарий с `DATABASE_URL` и замените
USER/PASSWORD/адрес/имя БД фактическими значениями. Спецсимволы в логине и
пароле URL-кодируются. Не вставляйте секрет в командную строку, PR или логи.
Файл `.env` исключён из Git; переменные процесса имеют приоритет над ним.

| Переменная | Значение |
|---|---|
| `APP_ENV` | `test` (по умолчанию), `stage`, `prod`; неверное значение отклоняется |
| `DATABASE_URL` | `postgresql+psycopg://…`; для БД обязателен, для `/health` можно не задавать |

На TEST/STAGE/PROD используются отдельные базы, пользователи и секреты.
`APP_ENV` — метка окружения, она не переключает БД автоматически и не включает
отладку. Адрес каждого стенда задаётся через его `DATABASE_URL`; фактические
адреса стендов ещё не подтверждены. Значения настроек с секретами не логируются.
Доступ на порт БД разрешается только приложению и администратору.

Администратор PostgreSQL создаёт роль и пустую БД; пример внутри `psql`
под владельцем кластера (пароль вводится интерактивно):

```sql
CREATE ROLE studentledger LOGIN;
\password studentledger
CREATE DATABASE studentledger OWNER studentledger;
```

После настройки подключения и **backup существующей БД** по разделу ниже:

```bash
.venv/bin/python -m app.db.check
.venv/bin/alembic upgrade head
.venv/bin/alembic current
.venv/bin/alembic check
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

Ожидается успешное подключение, ревизия `0001 (head)`, отсутствие расхождений
с моделями и HTTP 200 на `/health`. `--no-access-log` исключает попадание
параметров URL в журнал Uvicorn; секреты всё равно нельзя передавать в URL.
При недоступной БД `app.db.check` завершается с кодом 1 и русским сообщением;
в журнале только тип ошибки и SQLSTATE, без DSN, SQL и параметров.
Подробности PostgreSQL изучаются администратором в закрытом журнале СУБД.
Миграции не выполняются автоматически при старте приложения.

## Модель и границы

| Таблица | Данные и ограничения |
|---|---|
| `users` | UUID PK, уникальный логин до 128 символов, поле хеша до 512 символов, три роли, активность |
| `students` | UUID PK, обязательный уникальный FK `user_id`, ФИО (отчество необязательно), год, форма обучения, группа |
| `audit_logs` | UUID PK, FK автора, UTC timestamp, операция, тип и UUID объекта, результат success/failure |
| `refresh_sessions` | UUID PK, FK пользователя, уникальный SHA-256 digest токена, время создания/истечения/отзыва |

Все FK используют RESTRICT при удалении, а не каскадное удаление истории.
Связь User–Student: у студента обязательно есть User; у пользователя может
не быть профиля или быть один. Соответствие роли профилю проверяется будущими
сервисами, одна только схема не реализует RBAC. Формы обучения пока не
ограничены перечислением, которого нет в ТЗ. Год ограничен форматом 1–9999;
проверки бизнес-диапазонов и входных форм появятся вместе с APP-03.
Имена до 100 символов, группа/форма до 64; обязательные строки не пустые.

`AuditLog.object_id` — ссылка на объект разных типов, поэтому не FK к одной
таблице; FK автора обязателен. Значения полей, персональные данные и секреты
в аудит не копируются. Запись изменения и аудита должна идти в одной
`transaction()`; ошибка откатывает обе. CRUD пока отсутствует.

`password_hash` предназначен только для готового Argon2id/bcrypt-хеша;
хеширование, первичный администратор и проверка пароля — APP-02.
Refresh-хранилище содержит digest и `revoked_at`; выдача, проверка и отзыв
токенов ещё не реализованы. Наличие таблиц не закрывает SEC-07/08/09/10.

## Backup и проверенное восстановление

Перед изменением **существующей** схемы остановить записи приложения и
снять backup. Потребуются клиентские `psql`, `pg_dump`, `pg_restore`, `createdb`
той же основной версии, что сервер (или совместимой более новой).
Настройте `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` на нужную БД.
Пароль храните в защищённом `~/.pgpass` с правами 600 либо вводите по запросу
клиента; не помещайте его в аргументы команд. Указанные ниже имена файлов
уникальны по времени; резервные копии содержат чувствительные данные.

Из корня репозитория в bash/zsh:

```bash
umask 077
mkdir -p db/backups
backup_file="db/backups/before-migration-$(date +%Y%m%d-%H%M%S).dump"
pg_dump --format=custom --file="$backup_file" && pg_restore --list "$backup_file"
```

Если любая команда завершилась с ошибкой, миграцию не запускать.
Записать фактический путь backup и текущую ревизию `alembic current`.
Проверить восстановление в **новую пустую** БД с отдельным именем; пример:

```bash
createdb studentledger_restore_check
pg_restore --exit-on-error --no-owner --no-privileges \
  --dbname=studentledger_restore_check "$backup_file"
psql --dbname=studentledger_restore_check -v ON_ERROR_STOP=1 \
  -c 'SELECT version_num FROM alembic_version;' \
  -c 'SELECT count(*) FROM users;' \
  -c 'SELECT count(*) FROM students;' \
  -c 'SELECT count(*) FROM audit_logs;' \
  -c 'SELECT count(*) FROM refresh_sessions;'
```

Для backup до первой миграции таблиц ещё нет: проверяется успешное
восстановление пустой схемы. Для существующих данных сравнить ревизию,
число строк и контрольные записи/UUID/связи/даты с исходной БД.
Код выхода 0 без сравнения данных недостаточен.
Перед миграцией убедиться, что `DATABASE_URL` и настройки `PG*` указывают
на одну целевую БД. Затем `alembic upgrade head` и `alembic check`.

При неудаче не удалять рабочую БД и не выполнять `downgrade base` для её
«ремонта»: начальная downgrade удаляет все четыре таблицы и данные.
Восстановить backup в новую БД, проверить её, остановить приложение,
переключить секрет `DATABASE_URL` на восстановленную БД и прежнюю версию
кода, выполнить `app.db.check`, запустить и проверить приложение. Вернуть
рабочие записи только после проверки. Исходную БД сохранить для разбора.
Backup не включать в Git; доступ и хранение копий — ответственность владельца
стенда. Автоматизация backup/deploy относится к ЛР8.

## Тесты

Без PostgreSQL (проверки конфигурации, ошибок и `/health`):

```bash
.venv/bin/python -m pytest -q -m 'not integration'
```

Для полной проверки администратор создаёт отдельную **одноразовую** БД с
суффиксом `_test`. Задайте её URL через переменную `TEST_DATABASE_URL`
(в защищённом окружении, не в Git и не в `.env.example` с реальным паролем):

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
```

Интеграционные тесты очищают четыре таблицы и проверяют downgrade/upgrade;
их нельзя запускать против общей БД или базы с нужными данными. Суффикс —
лишь дополнительная защита, не доказательство изоляции. Без переменной
интеграционные тесты **пропускаются**, такой результат не считается полной
проверкой APP-01. Ожидается отсутствие skipped в полном прогоне.

Локальный результат: [evidence APP-01](evidence/app-01-foundation.md).
Реализация транзакций опирается на [SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html),
миграций — на [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html),
восстановления — на [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).
