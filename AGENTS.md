# AGENTS.md — StudentLedger

## Назначение

Этот репозиторий содержит учебный проект **StudentLedger** для дисциплины
«Автоматизация процессов жизненного цикла программных средств».

Перед любой работой агент обязан прочитать:

1. `docs/PROJECT_CONTEXT.md`
2. `docs/LABS_STATUS.md`
3. `docs/DECISIONS.md`
4. `docs/REQUIREMENTS_MAP.md`
5. `HANDOFF.md`
6. актуальное ТЗ ЛР1 и методические материалы, если они находятся в репозитории.
7. `docs/LABS_PLAN.md` и раздел «Совместная работа» в `README.md`.

## Передача работы между участниками

Инструкции обращены к **текущему исполнителю**. Задачи не закрепляются
за конкретными людьми. По умолчанию работа передаётся последовательно;
перед началом текущий исполнитель согласует с командой, что задача свободна.

- После получения изменений заново прочитать контекст из файлов. История
  чата, локальные процессы, `.venv` и доступы других участников не переносятся.
- Проверить `git status`, текущую ветку и remote. При отсутствии Git/remote
  указать, что именно требуется настроить. Не придумывать URL и доступы.
- При незакоммиченных изменениях не выполнять pull, переключение ветки,
  reset или автоматический stash поверх чужой работы. Сначала выяснить её статус.
- Определить одну текущую задачу, её границы и критерий готовности из
  `HANDOFF.md` и плана. Не переходить через незавершённые зависимости ЛР.
- Выполнять доступную агенту работу до завершения. Для недоступного действия
  дать текущему исполнителю точные команды/шаги GUI, место выполнения,
  ожидаемый результат, способ проверки и перечень evidence. Ожидание
  ручного шага не означает завершение всей лабораторной.
- Обновлять `HANDOFF.md` после каждого рабочего этапа, включая частичный
  результат: задача, изменения, выполненные проверки, ограничения, следующий
  шаг, необходимые действия и evidence. Сохранять актуальные незакрытые пункты.
- В том же наборе изменений обновлять затронутые решения, статусы и карту
  требований. Код и описывающий его контекст передавать вместе.
- Перед commit проверить diff и состав файлов; не включать секреты,
  локальные окружения и несвязанные изменения. После разрешённого commit/push
  сообщить фактическую ветку, SHA и результат push. Если push не выполнен,
  явно назвать причину и команды для завершения передачи.
- При параллельной работе использовать отдельные ветки с согласованными
  границами задач и PR. Конфликты context-файлов разрешать по фактическому
  состоянию обеих задач, не отбрасывая одну из сторон целиком.

Для всех передач достаточно существующего `HANDOFF.md`; отдельные реестры
задач и персональные назначения не требуются. Для всех изменений, включая инструкции и отчёты, действует ADR-009:
временные feature/fix/docs/chore от dev → PR в dev → выпуск PR dev в prod.
Подробные правила, обязательные проверки и переход с master — в README.
Прямые изменения общей dev/prod не являются рабочим процессом.
Документация к коду и HANDOFF передаются в том же PR; отдельная правка
документации — docs/*. Наличие правил не означает готовности CI/CD.

## Source of truth

Актуальное техническое задание ЛР1 — главный источник требований к продукту.
Методические материалы — главный источник требований к конкретной лабораторной работе.

Если ТЗ и методичка противоречат друг другу:
- не исправлять противоречие молча;
- зафиксировать его в `docs/DECISIONS.md`;
- предложить минимальное изменение;
- получить решение человека до изменения требований.

Если запрос пользователя явно противоречит условию задания ЛР:
- до выполнения противоречащего действия явно сообщить об этом пользователю;
- указать номер ЛР, конкретный пункт задания и источник (файл и страницу
  либо раздел), привести требование и объяснить, какая часть запроса ему
  противоречит;
- предложить минимальный вариант выполнения, соответствующий заданию;
- если пользователь после предупреждения явно выбирает отступление,
  зафиксировать решение и последствия в `docs/DECISIONS.md` и `HANDOFF.md`;
  не выдавать отступление за выполнение исходного условия ЛР;
- не объявлять противоречием собственные предпочтения агента или ограничения,
  которых нет в задании. При неоднозначности обозначить её как вопрос для
  уточнения, а не как установленное нарушение.

## Правила работы

- Не расширять функциональность без необходимости.
- Не менять стек и модель ролей без отдельного решения.
- Не хранить секреты в Git.
- Все изменения схемы БД выполнять через Alembic после его появления в проекте.
- Не заявлять о выполнении ручных действий, которые агент не может проверить.
- Не выдумывать скриншоты, IP-адреса, результаты запуска, статусы пайплайна и тестов.
- Любые реальные результаты от человека фиксировать в `HANDOFF.md` и `docs/evidence/`.
- После завершения каждой ЛР обновлять `docs/LABS_STATUS.md`.
- Новые архитектурные решения записывать в `docs/DECISIONS.md`.
- Изменения реализации связывать с идентификаторами требований в `docs/REQUIREMENTS_MAP.md`.

## Формат работы по каждой ЛР

Каждая лабораторная состоит из трёх частей:

1. **Agent work** — что агент может подготовить/реализовать сам.
2. **Human work** — что человек должен физически выполнить в GUI, на ВМ, в TeamCity, Docker Hub и т. п.
3. **Report** — после подтверждения реальных результатов агент создаёт отчёт по ЛР, аналогичный по стилю ЛР1.

ЛР считается `DONE` только когда готовы все три части.

## Обязательный финальный ответ агента по этапу

В конце каждого этапа агент должен вывести:

- что сделано;
- какие файлы изменены;
- какие команды выполнить;
- что должен сделать человек;
- критерии готовности Agent work;
- критерии готовности Human work;
- список evidence/скриншотов;
- что осталось;
- что записано в `HANDOFF.md`;
- готов ли этап к созданию отчёта.
